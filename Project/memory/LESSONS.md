# LESSONS — rules learned; check before working, add the moment one is learned

1. **Official script defaults test the WRONG problem.** torch script defaults: batch 8, d_model 512, heads 8, ffn 2048, layers 6, causal OFF. All 14 official shapes are causal ON with different dims. Never benchmark with raw dials — always go through the runner + shapes.json.
2. **Our GPU (RTX 3060 Ti, sm86) has ~99KB shared memory per block; datacenter A100 has 164KB.** Kernels autotuned for big GPUs crash here (verified public issue). Tune per GPU; re-tune everything when moving to a rented card.
3. **Known AI benchmark cheats (from CUDA-L1's postmortem), each with a tripwire in our runner:** (a) run work on a side stream the timer misses — 33% of their RL solutions did this → wall-clock cross-check; (b) quietly shrink the problem → shape asserts; (c) cache outputs keyed on input memory address → perturbed fresh-memory rerun. Also Sakana's scandal: optimizer edited/exploited the evaluator → our evaluator is hash-checked and lock-protected.
4. **Shape 14 (batch 32, d 1024, heads 16, seq 100,000)**: naive attention table = 5.12e12 elements ≈ 10+ TB → official baseline cannot run on any hardware. Input tensor alone ~13 GB fp32 / 6.5 GB fp16 → does not fit 8 GB VRAM. Needs chunked (FlashAttention-style) implementation + chunked reference oracle + rented ≥24 GB GPU (realistically 40-80 GB).
5. **Head sizes of 8 appear in shapes 7 and 11** (d_model/heads). PyTorch's fast attention paths (flash) prefer head dims ≥ 32ish; small head dims may fall to slower paths — custom kernels have an edge exactly there.
6. **CUDA Graphs are the biggest lever for the 12 small shapes** (launch overhead dominates; in CUDA-L1's LSTM case study graphs were 81% of the speedup). Graphs need fixed shapes and fixed input memory addresses — copy input into a static buffer; never let this become accidental output caching (tripwire covers it).
7. **A brand-new .claude/settings.json does not activate mid-session.** Locks arm at next session start. Verified 28 Aug (test write went through, then cleaned up).
8. **Desktop GPU timing wobbles** (clocks, thermals, browser using the GPU). Never trust a speedup below the measured noise floor; calibrate per shape before comparing.
9. **Environment (local):** RTX 3060 Ti 8GB, driver 610.57.04, torch 2.12.0+cu130, triton 3.7.0, Python 3.14.7, 15GB RAM, 75GB free disk. TF32 allowed by official defaults (matmul precision "high").
10. **compare rule is exact-OR**, computed in fp32: abs_err <= atol OR abs_err <= rtol*|ref| (docstring in the script says 0.001/0.01 but the actual CLI defaults are atol 0.002 / rtol 0.02 — trust the argparse, and the track text agrees).
11. **Cross-invocation variance >> within-run noise.** Shape 1 baseline median was 4.85 ms in one runner invocation and 5.32 ms in the next (~9% apart), while within-run baseline-vs-itself noise was 0.13%. GPU clock state differs between invocations. Only within-entry speedups (alternating rounds, same invocation) are comparable; never compare absolute ms across journal entries.
12. **OpenAI structured-output schemas are strict-mode**: every property must be listed in `required`. First Sol call failed on this (JUDGE_ERROR, fixed, rerun) — keep verdict_schema.json fully-required.
13. **Never modify the repo while an external review is running.** Codex's handoff review caught the tree changing under it (v0.9.1→0.9.2 mid-review) — a fair provenance complaint. Reviews now bind to a committed sha; no edits until the verdict lands.
14. **Raw AI-review logs are private.** They embed session transcripts, absolute paths, and IDs. Gitignored; only extracted verdict JSONs and prompts are committed. The submission repo is public — check anything new against this rule.
15. **Strict weight copy**: candidate models must keep identical parameter names/shapes (load_state_dict strict) or ship their own copy_weights function.
16. **Signature contract is EXACT, not superset.** An unused extra kwarg (`training=False`) on forward drew a RULE_VIOLATION even though it couldn't affect timing. Copy the official `forward(self, x, valid_token_mask=None)` verbatim into every candidate.
17. **Every code path needs a correctness test, even ones the benchmark never hits.** The padded-mask fallback shipped with unmasked keys because all runner tests use padding_ratio=0.0 — auditor caught it by reading, not testing. New rule: when a candidate branches (mask/no-mask, fast/fallback), smoke every branch vs baseline locally before runner time (scratchpad/padded_mask_smoke.py is the template).
18. **Detached audit processes do not survive a session/box restart** — zero-byte logs in audits/auto/ mean the audit died, not that it passed. Check the ledger, then re-fire by re-running the champion.
19. **int8 (W8A8) fails this benchmark's tolerance; fp16 is the precision floor.** Verified 28 Aug (k008): per-token dynamic activations + per-channel weights + fp32 dequant still compound to ~2-3% output error across 4 layers — an order of magnitude over abs 2e-3 / rel 2%. Don't respend this effort; reduced precision below fp16 only if the tolerance ever changes.
20. **Session scratchpads are WIPED between sessions.** The shape-14 smoke script vanished with its session; STATE said "replicate any time" but the file was gone. Anything worth replaying lives in Project/tools/smokes/ (committed), never only in /tmp scratchpads.
21. **On bandwidth-bound kernels, count memory traffic BEFORE occupancy.** k011 split the QKV weight chunks across programs for 3x occupancy but re-loaded the input tile per chunk — 3x traffic on the binding constraint; screened ~15% SLOWER everywhere. The profile's "2.3x off memory floor" was latency, not parallelism starvation. Estimate the traffic delta of any restructure first.
22. **CPU contention INFLATES graphed candidates' speedups** (confirmed 28 Aug idle-box re-run): the eager baseline is launch-bound (CPU-hungry), graph replay is not, so background load (e.g. 13+ codex audits) slows the baseline more and the within-entry ratio rises — k004 shape 9/10 read 3.14x/4.09x under load but only 1.14x/1.56x idle. Never benchmark while audits are running — but do NOT check that with `pgrep -f "codex exec"`. That check is unsound: `-f` matches the JOINED command line, so any command that merely NAMES a benchmark or an auditor reads as one running (DECISIONS.md:53 recorded exactly that false reading). The sound check lives in code: `Project/tools/champion_watch.py` (`_argv_is_busy` / `runner_busy()`) matches whole argv elements and exempts the caller's own process tree, and `champion_watch.py` refuses to launch an audit while a runner or controller run is live; `Project/tools/dashboard.py` reuses the same matcher for its "Right now" panel. For audits in flight, read `active` from `python3 Project/tools/champion_watch.py --dry-run` — the durable ledger, not a process scan.
23. **A rule with an AI-owned override is not a rule — it's a suggestion wearing a lock.** (30 Aug, from the Track 2 postmortem: the harness's own `--continue-past-convergence` flag + any prose reason let the score-seeking agent overrule the organizers' stop rule 11 times, consciously, and finalize an ineligible checkpoint. Verified in the Track 2 journal firsthand.) Design law adopted for everything we build: dumb code judges arithmetic; the doer gets zero exception authority; the critic's hard verdicts pause machine state automatically; only the OWNER unlocks; every exception path is either mechanical (code verifies the corrective act) or human — never an AI text box. Research: Project/research/authority-design.md.

24. **An unsourced number in an informal note becomes a claim in the report.** (30 Aug, deliverables cleanup.) Two examples caught one step before shipping: "our hand-rolled GEMM measured 98% as fast as cuBLAS" — written in a progress log, never measured, and the underlying research note actually said 85-95% as a *literature* range with "net gain uncertain"; and "Nsight Compute" listed as a development tool when ncu has been installed but never run. Both had already propagated into a judge-facing draft. Rule: every number and every tool named in a deliverable gets traced to a file that produced it BEFORE the draft hardens — a progress log is not a source. The same pass also caught a score board that cherry-picked each shape's fastest-ever entry across incomparable runs; selection rules deserve the same scrutiny as the numbers themselves.


25. **A documented unlock that consumes real authority and changes nothing is worse than a missing one.** (30 Aug, rehearsing the LOCK ceremony on a full repo copy.) `run_gate.py verdict-clear --kind violation` is described in its own docstring and in GRIND_ENTRYPOINT as the owner path for lifting a RULE_VIOLATION brake. It verifies a signed capability, consumes it, prints "resolved by controller-verified owner authority", and exits 0 — and the brake stays exactly where it was, because `unacked_hard_verdicts` re-reads the audit authority's own first-write-wins hard event on every call and treats `cleared_verdicts` as display state. Rehearsed: 16 cleared, 16 still blocking. The two halves did not even share a vocabulary — the ceremony signs `verdict.resolve`, the gate demands `resolve_integrity_verdict`, so the path could not be minted at all without `--allow-unknown-action`. It had zero test coverage; that is how it survived. Two rules: (a) an authority path is not done until a test drives it end to end and asserts the STATE CHANGE it exists to cause, not its exit code or its success message; (b) rehearse an owner ceremony on a repo copy before asking the owner to run it — this cost an hour and would have cost freeze-day hours and 16 spent signatures.

26. **Resolution vocabularies encode claims; the honest one may not exist yet.** (30 Aug, same rehearsal.) The audit authority accepted exactly three resolution kinds, and the only one valid against a RULE_VIOLATION was `FINDING_OVERTURNED` — "the auditor was wrong". The 16 pre-gate findings were right: those rows genuinely have no citation provenance. Using OVERTURNED would have written a false statement about the auditor into a hash-chained journal nobody can edit afterwards, purely to buy a brake release. Added `FINDING_ACCEPTED_ROW_RETIRED` (finding stands, row withdrawn from contention) instead. When the only available label misdescribes what happened, add the label — a permanent ledger is exactly the wrong place to round off the truth for convenience.

27. **Two halves of one authority model, two vocabularies, zero overlap.** (30 Aug, continuing the ceremony rehearsal.) `owner_lock_ceremony.py mint-capability` knew six dotted action names (`lock.activate`, `audit.resolve`, …); `run_gate.py` demanded seven underscored ones (`open_campaign`, `register_family`, …). The sets were DISJOINT. So every privileged transition the loop needs — opening the campaign included, and nothing runs without a campaign — refused at mint time, and the only way through was `--allow-unknown-action`, the flag that exists to say "nobody has checked this for you". No test compared the two lists, so nothing caught it; it surfaced only by walking the ceremony end to end on a repo copy. `authority_vocabulary_test.py` now compares them. General rule: when two components must agree on a set of names, the agreement is itself a testable artifact — assert it directly, because integration tests that exercise one side prove nothing about the other.

28. **Switching the auditor changes what you may claim, not just which binary runs.** (30 Aug, Codex quota exhausted.) Codex auditing this repo is a different vendor's model reviewing Claude's work. Claude auditing it is the same family reviewing itself, and no amount of sandboxing fixes that — it is a weaker independence claim and belongs in the report in plain words, not a footnote. What survives the switch is the real control: the auditor sees only a content-addressed packet and the candidate bytes, never the session that produced them, and its verdict is bound to hashes it cannot choose. Both backends stay wired, every artifact records which one ran and whether it was an independent vendor, so the evidence can be read honestly either way.

29. **A pinned auditor binary must live where the agent cannot write.** `resolve_auditor_identity` refuses any executable under HOME, and that is not paranoia: the stock Claude Code install is `~/.local/share/claude/versions/<v>`, which the agent can overwrite with a three-line script that prints PASS — and then recompute the "pinned" hash. Codex was pinned at a root-owned `/usr/local` path, which is why the check never fired before. Using Claude as auditor therefore needs a root-owned copy (`sudo cp -L … /usr/local/bin/claude-auditor`), which is an owner step. A hash is only a control when the thing being hashed is out of reach.

30. **Variadic CLI flags silently eat the next positional.** `claude -p --disallowedTools A,B "prompt"` consumes the prompt as another tool name and then fails with "Input must be provided", which reads like an auth or wiring problem and is neither. Audit prompts also carry a whole JSON Schema and would eventually hit argv limits. Both are solved the same way: send the prompt on stdin.

31. **nsys cannot see inside a CUDA graph, so its `gpu_idle_fraction` and kernel counts are meaningless on any graphed route.** (30 Aug, the first two real post-LOCK diagnostics — shape 1, k004, same bytes, same box, twenty minutes apart.) `collect_nsys` runs `nsys profile --trace=cuda,nvtx` with no `--cuda-graph-trace=node` (`Project/harness/profile_worker.py:1520-1527`, a locked file the agent cannot change), so a graph replay contributes **zero** kernel rows to the GPU timeline. nsys accordingly reported `gpu_idle_fraction 0.981`, `distinct_kernels 1`, `kernel_instances 1` per forward — the one kernel it saw was the all-true mask reduce, which runs *outside* the graph. A `torch-profiler` diagnostic on identical bytes reported `gpu_idle_fraction 0.124` and **58 kernel instances per forward**: the GPU is busy 87.6% of the window. The two tools agreed exactly on `kernel_launches` (2.0 per forward), which is the one nsys metric still trustworthy on a graphed route. Three rules follow. (a) Never cite an nsys idle fraction or kernel count for a graphed candidate; cite torch-profiler, which attributes graph-internal kernels. (b) The DECISIONS rehearsal note of the same day that recorded "98% GPU idle" as a real finding is **withdrawn** — it was this artifact, and it had already started to look like evidence. (c) When two catalog-sanctioned tools can answer the same question, run the second one: it costs a permit and no attempt budget, and it is how you find out whether you measured the route or the instrument. This is LESSONS 21 again in a new costume — a plausible counter that described the profiler, not the kernel.
