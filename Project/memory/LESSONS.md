# LESSONS — rules learned; check before working, add the moment one is learned

1. **Official script defaults test the WRONG problem.** torch script defaults: batch 8, d_model 512, heads 8, ffn 2048, layers 6, causal OFF. All 14 official shapes are causal ON with different dims. Never benchmark with raw dials — always go through the runner + shapes.json.
2. **Our GPU (RTX 3060 Ti, sm86) has ~99KB shared memory per block; datacenter A100 has 164KB.** Kernels autotuned for big GPUs crash here (verified public issue). Tune per GPU; re-tune everything when moving to a rented card.
3. **Known AI benchmark cheats (from CUDA-L1's postmortem), each with a tripwire in our runner:** (a) run work on a side stream the timer misses — 33% of their RL solutions did this → wall-clock cross-check; (b) quietly shrink the problem → shape asserts; (c) cache outputs keyed on input memory address → perturbed fresh-memory rerun. Also Sakana's scandal: optimizer edited/exploited the evaluator → our evaluator is hash-checked and lock-protected.
4. **Shape 14 (batch 32, d 1024, heads 16, seq 100,000)**: naive attention table = 5.12e12 elements ≈ 10+ TB → official baseline cannot run on any hardware. Input tensor alone ~13 GB fp32 / 6.5 GB fp16 → does not fit 8 GB VRAM. Needs chunked (FlashAttention-style) implementation + chunked reference oracle + rented ≥24 GB GPU (realistically 40-80 GB).
5. **Head sizes of 8 appear in shapes 7 and 11** (d_model/heads). PyTorch's fast attention paths (flash) prefer head dims ≥ 32ish; small head dims may fall to slower paths — custom kernels have an edge exactly there.
6. **CUDA Graphs are the biggest lever for the 12 small shapes** (launch overhead dominates; in CUDA-L1's LSTM case study graphs were 81% of the speedup). Graphs need fixed shapes and fixed input memory addresses — copy input into a static buffer; never let this become accidental output caching (tripwire covers it).
7. **A brand-new .claude/settings.json does not activate mid-session.** Locks arm at next session start. Verified 28 Aug (test write went through, then cleaned up).
8. **Desktop GPU timing wobbles** (clocks, thermals, browser using the GPU). Never trust a speedup below the measured noise floor; calibrate per shape before comparing.
9. **Environment (local):** RTX 3060 Ti 8GB, driver 610.57.04, torch 2.12.0+cu130, triton 3.7.0, Python 3.14.7, 15GB RAM, 75GB free disk. TF32 allowed by official defaults (matmul precision "high").
10. **compare rule is exact-OR**, computed in fp32: abs_err <= atol OR abs_err <= rtol*|ref| (docstring in the script says 0.001/0.01 but the actual CLI defaults are atol 0.002 / rtol 0.02 — trust the argparse, and the track text agrees).
11. **Cross-invocation variance >> within-run noise.** Shape 1 baseline median was 4.85 ms in one runner invocation and 5.32 ms in the next (~9% apart), while within-run baseline-vs-itself noise was 0.13%. GPU clock state differs between invocations. Only within-entry speedups (alternating rounds, same invocation) are comparable; never compare absolute ms across journal entries.
12. **OpenAI structured-output schemas are strict-mode**: every property must be listed in `required`. First Sol call failed on this (JUDGE_ERROR, fixed, rerun) — keep verdict_schema.json fully-required.
13. **Never modify the repo while an external review is running.** Codex's handoff review caught the tree changing under it (v0.9.1→0.9.2 mid-review) — a fair provenance complaint. Reviews now bind to a committed sha; no edits until the verdict lands.
14. **Raw AI-review logs are private.** They embed session transcripts, absolute paths, and IDs. Gitignored; only extracted verdict JSONs and prompts are committed. The submission repo is public — check anything new against this rule.
15. **Strict weight copy**: candidate models must keep identical parameter names/shapes (load_state_dict strict) or ship their own copy_weights function.
16. **Signature contract is EXACT, not superset.** An unused extra kwarg (`training=False`) on forward drew a RULE_VIOLATION even though it couldn't affect timing. Copy the official `forward(self, x, valid_token_mask=None)` verbatim into every candidate.
17. **Every code path needs a correctness test, even ones the benchmark never hits.** The padded-mask fallback shipped with unmasked keys because all runner tests use padding_ratio=0.0 — auditor caught it by reading, not testing. New rule: when a candidate branches (mask/no-mask, fast/fallback), smoke every branch vs baseline locally before runner time (scratchpad/padded_mask_smoke.py is the template).
18. **Detached audit processes do not survive a session/box restart** — zero-byte logs in audits/auto/ mean the audit died, not that it passed. Check the ledger, then re-fire by re-running the champion.
19. **int8 (W8A8) fails this benchmark's tolerance; fp16 is the precision floor.** Verified 28 Aug (k008): per-token dynamic activations + per-channel weights + fp32 dequant still compound to ~2-3% output error across 4 layers — an order of magnitude over abs 2e-3 / rel 2%. Don't respend this effort; reduced precision below fp16 only if the tolerance ever changes.
20. **Session scratchpads are WIPED between sessions.** The shape-14 smoke script vanished with its session; STATE said "replicate any time" but the file was gone. Anything worth replaying lives in Project/tools/smokes/ (committed), never only in /tmp scratchpads.
21. **On bandwidth-bound kernels, count memory traffic BEFORE occupancy.** k011 split the QKV weight chunks across programs for 3x occupancy but re-loaded the input tile per chunk — 3x traffic on the binding constraint; screened ~15% SLOWER everywhere. The profile's "2.3x off memory floor" was latency, not parallelism starvation. Estimate the traffic delta of any restructure first.
22. **CPU contention INFLATES graphed candidates' speedups** (confirmed 28 Aug idle-box re-run): the eager baseline is launch-bound (CPU-hungry), graph replay is not, so background load (e.g. 13+ codex audits) slows the baseline more and the within-entry ratio rises — k004 shape 9/10 read 3.14x/4.09x under load but only 1.14x/1.56x idle. Never benchmark while audits are running — but do NOT check that with `pgrep -f "codex exec"`. That check is unsound: `-f` matches the JOINED command line, so any command that merely NAMES a benchmark or an auditor reads as one running (DECISIONS.md:53 recorded exactly that false reading). The sound check lives in code: `Project/tools/champion_watch.py` (`_argv_is_busy` / `runner_busy()`) matches whole argv elements and exempts the caller's own process tree, and `champion_watch.py` refuses to launch an audit while a runner or controller run is live; `Project/tools/dashboard.py` reuses the same matcher for its "Right now" panel. For audits in flight, read `active` from `python3 Project/tools/champion_watch.py --dry-run` — the durable ledger, not a process scan.
23. **A rule with an AI-owned override is not a rule — it's a suggestion wearing a lock.** (30 Aug, from the Track 2 postmortem: the harness's own `--continue-past-convergence` flag + any prose reason let the score-seeking agent overrule the organizers' stop rule 11 times, consciously, and finalize an ineligible checkpoint. Verified in the Track 2 journal firsthand.) Design law adopted for everything we build: dumb code judges arithmetic; the doer gets zero exception authority; the critic's hard verdicts pause machine state automatically; only the OWNER unlocks; every exception path is either mechanical (code verifies the corrective act) or human — never an AI text box. Research: Project/research/authority-design.md.

24. **An unsourced number in an informal note becomes a claim in the report.** (30 Aug, deliverables cleanup.) Two examples caught one step before shipping: "our hand-rolled GEMM measured 98% as fast as cuBLAS" — written in a progress log, never measured, and the underlying research note actually said 85-95% as a *literature* range with "net gain uncertain"; and "Nsight Compute" listed as a development tool when ncu has been installed but never run. Both had already propagated into a judge-facing draft. Rule: every number and every tool named in a deliverable gets traced to a file that produced it BEFORE the draft hardens — a progress log is not a source. The same pass also caught a score board that cherry-picked each shape's fastest-ever entry across incomparable runs; selection rules deserve the same scrutiny as the numbers themselves.


25. **A documented unlock that consumes real authority and changes nothing is worse than a missing one.** (30 Aug, rehearsing the LOCK ceremony on a full repo copy.) `run_gate.py verdict-clear --kind violation` is described in its own docstring and in GRIND_ENTRYPOINT as the owner path for lifting a RULE_VIOLATION brake. It verifies a signed capability, consumes it, prints "resolved by controller-verified owner authority", and exits 0 — and the brake stays exactly where it was, because `unacked_hard_verdicts` re-reads the audit authority's own first-write-wins hard event on every call and treats `cleared_verdicts` as display state. Rehearsed: 16 cleared, 16 still blocking. The two halves did not even share a vocabulary — the ceremony signs `verdict.resolve`, the gate demands `resolve_integrity_verdict`, so the path could not be minted at all without `--allow-unknown-action`. It had zero test coverage; that is how it survived. Two rules: (a) an authority path is not done until a test drives it end to end and asserts the STATE CHANGE it exists to cause, not its exit code or its success message; (b) rehearse an owner ceremony on a repo copy before asking the owner to run it — this cost an hour and would have cost freeze-day hours and 16 spent signatures.

26. **Resolution vocabularies encode claims; the honest one may not exist yet.** (30 Aug, same rehearsal.) The audit authority accepted exactly three resolution kinds, and the only one valid against a RULE_VIOLATION was `FINDING_OVERTURNED` — "the auditor was wrong". The 16 pre-gate findings were right: those rows genuinely have no citation provenance. Using OVERTURNED would have written a false statement about the auditor into a hash-chained journal nobody can edit afterwards, purely to buy a brake release. Added `FINDING_ACCEPTED_ROW_RETIRED` (finding stands, row withdrawn from contention) instead. When the only available label misdescribes what happened, add the label — a permanent ledger is exactly the wrong place to round off the truth for convenience.

27. **Two halves of one authority model, two vocabularies, zero overlap.** (30 Aug, continuing the ceremony rehearsal.) `owner_lock_ceremony.py mint-capability` knew six dotted action names (`lock.activate`, `audit.resolve`, …); `run_gate.py` demanded seven underscored ones (`open_campaign`, `register_family`, …). The sets were DISJOINT. So every privileged transition the loop needs — opening the campaign included, and nothing runs without a campaign — refused at mint time, and the only way through was `--allow-unknown-action`, the flag that exists to say "nobody has checked this for you". No test compared the two lists, so nothing caught it; it surfaced only by walking the ceremony end to end on a repo copy. `authority_vocabulary_test.py` now compares them. General rule: when two components must agree on a set of names, the agreement is itself a testable artifact — assert it directly, because integration tests that exercise one side prove nothing about the other.

28. **Switching the auditor changes what you may claim, not just which binary runs.** (30 Aug, Codex quota exhausted.) Codex auditing this repo is a different vendor's model reviewing Claude's work. Claude auditing it is the same family reviewing itself, and no amount of sandboxing fixes that — it is a weaker independence claim and belongs in the report in plain words, not a footnote. What survives the switch is the real control: the auditor sees only a content-addressed packet and the candidate bytes, never the session that produced them, and its verdict is bound to hashes it cannot choose. Both backends stay wired, every artifact records which one ran and whether it was an independent vendor, so the evidence can be read honestly either way.

29. **A pinned auditor binary must live where the agent cannot write.** `resolve_auditor_identity` refuses any executable under HOME, and that is not paranoia: the stock Claude Code install is `~/.local/share/claude/versions/<v>`, which the agent can overwrite with a three-line script that prints PASS — and then recompute the "pinned" hash. Codex was pinned at a root-owned `/usr/local` path, which is why the check never fired before. Using Claude as auditor therefore needs a root-owned copy (`sudo cp -L … /usr/local/bin/claude-auditor`), which is an owner step. A hash is only a control when the thing being hashed is out of reach.

30. **Variadic CLI flags silently eat the next positional.** `claude -p --disallowedTools A,B "prompt"` consumes the prompt as another tool name and then fails with "Input must be provided", which reads like an auth or wiring problem and is neither. Audit prompts also carry a whole JSON Schema and would eventually hit argv limits. Both are solved the same way: send the prompt on stdin.

31. **nsys cannot see inside a CUDA graph, so its `gpu_idle_fraction` and kernel counts are meaningless on any graphed route.** (30 Aug, the first two real post-LOCK diagnostics — shape 1, k004, same bytes, same box, twenty minutes apart.) `collect_nsys` runs `nsys profile --trace=cuda,nvtx` with no `--cuda-graph-trace=node` (`Project/harness/profile_worker.py:1520-1527`, a locked file the agent cannot change), so a graph replay contributes **zero** kernel rows to the GPU timeline. nsys accordingly reported `gpu_idle_fraction 0.981`, `distinct_kernels 1`, `kernel_instances 1` per forward — the one kernel it saw was the all-true mask reduce, which runs *outside* the graph. A `torch-profiler` diagnostic on identical bytes reported `gpu_idle_fraction 0.124` and **58 kernel instances per forward**: the GPU is busy 87.6% of the window. The two tools agreed exactly on `kernel_launches` (2.0 per forward), which is the one nsys metric still trustworthy on a graphed route. Three rules follow. (a) Never cite an nsys idle fraction or kernel count for a graphed candidate; cite torch-profiler, which attributes graph-internal kernels. (b) The DECISIONS rehearsal note of the same day that recorded "98% GPU idle" as a real finding is **withdrawn** — it was this artifact, and it had already started to look like evidence. (c) When two catalog-sanctioned tools can answer the same question, run the second one: it costs a permit and no attempt budget, and it is how you find out whether you measured the route or the instrument. This is LESSONS 21 again in a new costume — a plausible counter that described the profiler, not the kernel.

32. **Before crediting a mechanism, compute the ceiling that mechanism can possibly deliver.** (30 Aug, attempt 1 of CAMP-POSTLOCK, caught by the independent auditor and not by me.) I registered `F-shape1-graph` on bottleneck `launch-overhead`, measured k004 at **2.0748x**, and wrote it up as the graph-replay mechanism working. The bound baseline profile — which I had read myself and called "sensible" — says the shape-1 forward is **GPU-busy 96.6%** of its span: 114.578 ms busy inside a 118.567 ms span over 20 iterations, i.e. only **0.199 ms of host-launch idle per 5.93 ms forward**. Removing every one of the 113 eliminated launches therefore cannot buy more than about **1.035x**, which is essentially the shape's own 1.03 promotion threshold. The measured saving was 2.670 ms; launch removal can account for at most ~7% of it. The real cause is the *other* change bundled into the same file: k004 also replaces eager attention with an inlined flash-style Triton kernel plus a fused packed QKV projection, removing repeated traffic over a 16.8 MB per-layer score tensor. **I changed two things and credited the one I had a story for.** Rules: (a) for any mechanism claim, do the arithmetic that bounds it — idle fraction bounds launch removal, DRAM bytes bound fusion, FLOPs bound precision work — and refuse to open the family if the ceiling sits under the promotion threshold; (b) one candidate must isolate one variable, or the plan must declare up front that it measures a bundle and name the isolating run that will split it; (c) a result far ABOVE the band is as much a diagnosis failure as one below — I treated the overshoot as pleasant and it was the loudest possible signal that the registered mechanism was not what moved the number.

35. **I cannot forecast this system, and I preregistered what to do about it.** (30 Aug, CAMP-POSTLOCK screening sweep.) Eight prediction bands in one night, **eight misses**: 1.15 → 2.075, 2.10 → 1.601, 1.66 → 2.143, 1.85 → 2.147, 2.14 → 1.172, 1.56 → 1.583, 2.25 → 4.243, 3.50 → 5.810. Every method failed in turn — mechanism ceilings, cross-tool device-time arithmetic, work-density scaling, nearest-measured-analogue, a reproduced historical note, and finally a measured per-kernel time breakdown *of the shape being predicted*, which was the best-founded of them and still missed by 66%. On that last card I wrote in advance: "if this band also misses, the honest conclusion is that I cannot forecast this system and should report characterization runs as measurements without numeric bands." It missed. **Honouring that:** the gate requires `predict-min`/`predict-max` on every screening plan, so the field cannot be omitted — but from here it is filled as a *required field with stated low confidence*, never as a claim, and **no conclusion is drawn from a band hit or miss**. Conclusions come from the measurement. What stayed sound throughout is the scaffolding, and it is the transferable part: every run was `--prediction-kind characterization` in the scratch lane, so eight consecutive misses cost **zero strikes**, and six of them fired falsifiers deliberately aimed at my own position — which is what actually produced every real finding of the night (size is irrelevant, head count governs, an old note reproduces, hd=8 is a target not a wall, the fused kernel beats cuBLAS's attention GEMMs at long sequence). **Being consistently wrong is survivable when the cost of being wrong is bounded and the errors are instrumented; it is fatal when neither is true.**

34. **An idle-fraction ceiling is not a bound on what a mechanism can buy, and a critic's argument is a hypothesis, not a finding.** (30 Aug, 23:17–23:20, twenty minutes end to end.) The auditor argued — and I accepted, wrote into DECISIONS as settled, and committed — that because the shape-1 baseline is GPU-busy 96.6% of its span, CUDA-graph replay could recover at most ~1.035x. Two screening runs on a verified deep-idle box: **k003 (Triton attention, no graph) 1.6010x; k004 (same kernel + graph) 2.1428x**, so the capture is worth **1.338x**, not 1.035x. The ceiling failed for three reasons worth remembering: it was computed **under the profiler** (nsys span 5.928 ms/iter against an unprofiled 5.154 ms/iter median, a 15% inflation of the very denominator); `gpu_busy_ns` sums kernel durations so sub-resolution gaps count as busy; and decisively, **graph replay removes real device work, not just idle time** — the baseline issues 17 `cudaMemcpyAsync` and 24 `cudaMemsetAsync` per forward whose cost sits *inside* the busy side that the ceiling treats as irreducible. `1/(1 - idle_fraction)` is not an upper bound on a mechanism that deletes work from the numerator. Two rules: (a) before quoting any ceiling, ask which quantity the mechanism actually changes and whether the ceiling's denominator can see it; (b) **an independent critic's quantitative argument gets tested, not adopted** — mine cost nothing to test and I committed the claim instead. What saved this was preregistering a falsifier that pointed at my own position ("if k004 on a quiet box lands at or above 2.0, the contention explanation is wrong and the ceiling must be wrong too"); it fired, and that is the entire reason the error lived twenty minutes instead of reaching the report.

36. **Check what the submission dispatches to BEFORE spending a campaign measuring it.** (31 Aug, found by reading the tech report's prose, not its tables.) Twenty-two consecutive post-LOCK attempts measured `k004_graphed_triton.py` and produced a clean, permitted, internally consistent twelve-shape board with a 2.94x geomean — of a kernel this submission **does not ship**. `Project/submission/dispatcher_region.py` routes `d_model <= 128` to the fused-block megakernel and larger `d_model` to an fp16 stack; re-measuring the actual routes gave **9.68x**, so the "correction" understated the shipped route by ~3.5x. Root cause: the runbook's step-11 worked example used k004, and I followed the example instead of the dispatcher. Three things made it survivable and one made it dangerous. Survivable: every run was screening-lane so nothing promoted; every run was permitted so the re-measurement was mechanical; the error was in *which* file, never in the measurement of it. Dangerous: the wrong board was **more defensible than the right one** — permitted, calibrated, reproducible — and it went into three judge-facing drafts as the corrected headline. **A measurement's provenance chain says nothing about whether you measured the right artifact.** Rule: the first step of any measurement campaign is to derive the target from the thing that ships — read the dispatcher, not the runbook example — and record that derivation in the plan so the binding is auditable. A worked example is a syntax demonstration, never a target selection.

37. **Withdrawing a number and disbelieving it are different acts; do not let the first slide into the second.** (31 Aug, the same campaign.) On finding the pre-gate board procedurally invalid — no permit, no bound verdict, baselines 6–63% off calibration — I withdrew it, correctly. Then I asserted it was "systematically inflated", which was an *empirical* claim I had not measured. Re-measuring all twelve shapes gave a mean delta of **−5.6%** with scatter **−22.4% to +21.6% in both directions**, uncorrelated with baseline device idle: the old board was approximately right and improperly obtained. I then over-corrected twice more in the same direction, each time promoting a fresh guess to a finding — "a constant 1.77x k009/k004 ratio" (actual range 1.76x–6.31x, from two points) and "the MFU table is inflated by the same factor" (recompute: 12.15 TF/s vs the table's 11.63, 4.5% apart). The pattern is one failure mode, not three: **on discovering an error I reached for the strongest available restatement of it rather than the narrowest true one.** The withdrawal needed no support beyond the process defect; every extra sentence I attached to it needed evidence and had none. Rule: when withdrawing, state exactly the defect that justifies the withdrawal and stop. What replaces the number is a measurement, not a stronger adjective.

38. **Measure the artifact that ships, not the module that resembles it — and "its header matches" is not a measurement.** (31 Aug, closing the campaign.) After correcting the wrong-kernel disaster, the twelve-shape board measured `k009_fused_tuned.py` and `k010_fused_ln.py`, chosen because their headers describe exactly what `dispatcher_region.py` describes. Card C18 even wrote the caveat down — "k009 is the megakernel CLASS the dispatcher ships, not literally the dispatcher bytes" — and then nobody tested it for two hours. `dispatcher_region.py` genuinely cannot be loaded standalone (it uses `BaselineTransformer` as a free name), but **`torch_transformer_benchmark_submission.py` can**, because it is the whole official script with one region replaced, and that had simply never been tried as a candidate impl. Measuring all twelve shapes on it moved the headline from **9.68x to 9.45x**. The move is small; the principle is not. A documentation match is a *better grade* of evidence than the runbook example that caused the original error, but it is the **same species** — reasoning about which bytes run instead of running them. Rule: at least once, measure the exact file that ships, on both sides of every branch it takes; the two-shape pair that exercises a routing predicate is worth more than ten that re-confirm one path. Corollary: when a caveat is written into a card, it is a task, not an absolution.

39. **A four-point pattern with a plausible mechanism is still a guess; preregister it out of sample and it costs one run to find out.** (31 Aug, the fixed-dispatch-cost model.) The first four shipped-file deltas ordered perfectly by candidate time — −0.008% at 19.06 ms, −0.44% at 5.86 ms, −1.96% at 0.570 ms, −8.69% at 0.121 ms — which is the signature of a fixed per-forward cost, and a mechanism was in plain sight: the shipped class inspects the shape on every call and the bare module does not. A fixed 10 µs fit all four to within half a percent. Everything about it was persuasive. I wrote it into card C32 with **eight out-of-sample point predictions before running any of them**. The very next shape came in **+2.62%, faster than its module**, which no fixed overhead can produce; and shapes 1, 9 and 10, whose candidate times agree within 4%, landed at −1.96%, −10.03% and −0.46%, so the gap does not track candidate time at all. It was cross-invocation scatter (LESSONS 11) the whole way. **Cost of being wrong: one screening run**, because the prediction was recorded before the data existed and could not be quietly reshaped afterwards. This is LESSONS 37's failure mode caught prospectively instead of by an auditor, and it is the second time in one night that preregistering a discriminator killed my own hypothesis cheaply (the other being the shape-11 K2 profile). Keep the dead model in the write-up: a pattern that dies on its fifth point is better methods-section material than a tidy model nobody tested.

40. **Every command a document tells someone to type is a claim, and it decays exactly like a number.** (31 Aug, hostile read of the drafts.) Three documents — the video script's live Scene 3, and the reproduce blocks of both the README and the tech report — told the reader to run `python3 Project/harness/runner.py run --shape 13 --impl …`. I ran it. It dies instantly with `error: the following arguments are required: --permit`, because the LOCK replaced `runner.py` with a 27-line shim onto the trusted controller and the controller times nothing without a one-use permit. The video script had "beats while it runs" written underneath a command that produces one line of argparse error, on camera, in the middle of the trust-chain scene. **Nobody had typed it since the LOCK.** Two rules: (a) re-run every command in every judge-facing document after any change to the harness, because a stale invocation is indistinguishable from a broken project to a reader who tries it; (b) when the failure is the enforcement boundary doing its job, *show the failure* — the refusal is better evidence for the claim than a successful run would be. Also worth checking the expiry on any credential a documented procedure depends on: the owner capabilities these runs need expire mid-way through the planned recording window.

41. **Check which arm of the comparison a table column describes before quoting it.** (31 Aug, same read.) Two drafts said shape 8's *baseline* was "already at 64% of the fp16 roofline before we touch it". The 64% is the **candidate's** figure, taken from the `cand ms` column of `roofline-table.md`; the baseline is at **0.34 MFU** (10.95 TF/s) and our kernel takes it to **0.68** (22.08 TF/s). The sentence asserted that our starting point was where we finished, and it made the honest result *worse*: 2.02× reads as scraping a nearly-full roofline, when what actually happened is that we **doubled achieved utilisation**. The qualitative claim (shape 8 is arithmetic-bound, least headroom on the board) was right, which is exactly why the wrong number survived several readings — a supporting figure that points the same direction as a true conclusion does not get challenged. This error also reached a gate plan hypothesis and is therefore in the immutable log, so it is corrected inline rather than silently. Same root as LESSONS 32 and 37: reading a derived column without checking what it was derived from.

42. **Count the ledger before describing it, and own the unflattering number.** (31 Aug, draft audit.) Two drafts said "60+ verdicts ... including the RULE_VIOLATIONs that made us change the code" — phrasing that reads like two violations. Counting all 81 lines gives **42 PASS, 28 RULE_VIOLATION, 8 NEEDS_CONTEXT, 3 RETEST**: rule violations are **35%** of the ledger, and it is a file a judge can open in one click. Reading two of them showed they are **procedural, not integrity** findings — pre-gate runs that cannot prove which plan produced them, with the auditor explicitly writing *"no evidence of timing or cache gaming"* and *"no timer manipulation, harness access, input mutation, or stale-output reuse"*. So the honest version is both more alarming and far more convincing than the euphemism: a third of our own audit ledger is the auditor rejecting our paperwork, none of it is the auditor catching us cheating, and we can quote it. **A number that looks bad in isolation and good in context should be published with the context, never rounded into a phrase** — the euphemism is what makes it look like concealment when someone checks. Corollary found the same pass: our seed count was *under*stated (seven trials, five fixed plus two random, not five), so "check the claim against the artifact" cuts both ways and sometimes hands you a better story than the one you wrote.

43. **Your own research base may already contain the finding you are about to spend a night deriving.** (31 Aug.) A verdict recorded on **29 Aug** states *"Shape 11's eager baseline is especially inefficient at 16 heads with head dimension 8"*. On 31 Aug I measured the head-count axis across shapes 1/9/10/11 and established exactly that — the baseline degrades 4.3x across the axis on identical FLOPs — treating it as a new discovery. The auditor had written it down two days earlier and it sat unread in `Project/audits/`. The measurement was still worth doing (it quantified what the auditor asserted, and quantification is what the report needs), but the *direction* to look was free and already paid for. Rule: before opening an investigation, search the audit responses and research notes for the question, not just the answer — the adversarial reviews in particular contain domain observations that were never the point of the review and therefore never got indexed anywhere.

33. **A verdict the ledger could not record is still a verdict.** (30 Aug, same attempt.) The auditor returned a complete document — integrity **RETEST**, technical **WEAK_DIAGNOSIS** — and `record_audit_result` refused it with "verdict does not match full schema", listing every required property as missing even though the stored response artifact plainly contains `schema_version`, `attempt_nonce`, `entry_id`, `packet_sha256`, `candidate_sha256`, `integrity`, `technical_review` and `summary`. So the run shows in the journal as `attempt_failed` / `AUDITOR_PROCESS_ABANDONED_WITHOUT_TERMINAL_EVENT` and no hard verdict is latched — the brake the design intends is simply absent. The temptation is obvious and must be named: an unrecorded hard verdict looks exactly like no verdict, and "absence is not a pass" (GRIND_ENTRYPOINT §7) is precisely the rule that stops you treating it as one. The finding was read out of the durable response artifact and acted on as binding. **Any audit-recording failure is a stop condition, not a retry loop**, because the retry cap (3) silently converts a systematic plumbing fault into "escalate to owner_attention" after burning three audits at roughly $2.49 each.
